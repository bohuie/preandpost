# SonarQube Metrics Definition

The **SonarQube quality model** is applied to an automated code review and analysis based on four types of rules. The four types included in the SonarQube quality model are:

- Reliability (bug)
- Maintainability (code smell)
- Security (vulnerability)
- Security Hotspot  
  We exclude this category because security hotspots are not confirmed vulnerabilities and require human review. They indicate security-sensitive code that requires manual review to determine whether it is actually risky. Since this study requires automated and consistently comparable metrics across pre- and post-AI repositories, Security Hotspots are excluded from the core analysis.

In this context, a **finding** refers to an individual issue detected by SonarQube in the source code. Each finding has a type, such as Bug, Vulnerability, or Code Smell, and contributes to the corresponding metric count.

## Software Quality Severities

| Software Quality Severities | Definitions |
|---|---|
| Blocker | An issue that has a significant probability of severe unintended consequences on the application that should be fixed immediately. This includes bugs leading to production crashes and security flaws allowing attackers to extract sensitive data or run malicious code. |
| High | An issue with a high impact on the application that should be fixed as soon as possible. |
| Medium | An issue with a medium impact on the application. |
| Low | An issue with a low impact on the application. |

## Security

Issues in this domain mark potential weaknesses to hackers. Security refers to the protection of software from unauthorized access, use, or destruction. The rules are divided into two types: **security-injection** and **security-configuration** rules.

Reference: https://docs.sonarsource.com/sonarqube-server/quality-standards-administration/managing-rules/security-related-rules

- **Security-injection:** Detects injection vulnerabilities when user-controlled input flows into sensitive functions without validation or sanitization.  
  Example flow: user input → sensitive function → without checking/cleaning.  
  Examples: CWE-89 SQL Injection, CWE-79 Cross-site Scripting, CWE-94 Code Injection.

- **Security-configuration rules:** Detects incorrect or weak security settings, such as passwords written directly in code, weak encryption, or overly open application access.  
  Examples: hard-coded credentials, CWE-1004 Sensitive Cookie Without `HttpOnly` Flag, CWE-297 Improper Validation of Certificate with Host Mismatch, CWE-327 Use of a Broken or Risky Cryptographic Algorithm.

Example:

```java
String password = "admin123";
String apiKey = "abc-123-secret";
```

| Metric | Description |
|---|---|
| Vulnerabilities | Number of vulnerabilities. Calculated from the number of issues generated by SonarQube rules with the **Vulnerability type**.<br><br>SonarQube scans the code against security language-specific rules. When the code matches a vulnerable pattern, SonarQube counts it as a vulnerability issue.<br><br>**Is the rule about code that could be exploited by an attacker?** If yes, then it is a vulnerability rule. |
| Security Rating | A–E rating based on the severity of detected vulnerabilities.<br><br>A = 0 Vulnerabilities<br>B = at least 1 Minor Vulnerability<br>C = at least 1 Major Vulnerability<br>D = at least 1 Critical Vulnerability<br>E = at least 1 Blocker Vulnerability |

## Reliability

Issues in this domain mark code where behavior may differ from what was expected. Reliability measures how software is capable of maintaining its level of performance under stated conditions for a stated period of time.

| Metric | Description |
|---|---|
| Bugs | Number of bugs.<br><br>**Is the rule about code that is demonstrably wrong, or more likely wrong than not?** If the answer is yes, then it is a bug rule. |
| Reliability Rating | Rating related to reliability. The rating grid is as follows:<br><br>A = 0 bug<br>B = at least 1 Minor bug<br>C = at least 1 Major bug<br>D = at least 1 Critical bug<br>E = at least 1 Blocker bug |

---

## Maintainability

Issues in this domain mark code that will be more difficult to update competently than it should be. Maintainability refers to the ease with which software code can be repaired, improved, and understood.

**Is the rule neither a bug nor a vulnerability?** If yes, then it is a maintainability rule.

| Metric | Description |
|---|---|
| Code Smells | Number of code smells. Is the rule neither a bug nor a vulnerability? If yes, then it is a code smell rule. |
| Debt | A measure of effort to fix all code smells, in minutes. An 8-hour day is assumed when values are shown in days. Therefore, 1 day = 8 working hours. |
| Debt Ratio | The ratio between the cost to develop the software and the cost to fix it.<br><br>**Formula:**<br>`Debt Ratio = Remediation Cost / Development Cost`<br><br>Expanded formula:<br>`Debt Ratio = Remediation Cost (estimated time to fix code smells) / (Cost to develop 1 line of code * Number of lines of code)`<br><br>Cost to develop 1 line of code = 0.06 days, approximately 30 minutes. |
| Maintainability Rating | The rating given to the project relative to the value of the debt ratio. The default Maintainability rating grid is:<br><br>A = 0–0.05<br>B = 0.06–0.1<br>C = 0.11–0.20<br>D = 0.21–0.5<br>E = 0.51–1<br><br>The Maintainability rating scale can also be stated as:<br><br>- <=5% of the time that has already gone into the application = A<br>- between 6% and 10% = B<br>- between 11% and 20% = C<br>- between 21% and 50% = D<br>- anything over 50% = E |

## Coverage

Reference: https://docs.sonarsource.com/sonarqube-server/2026.1/extension-guide/developing-a-plugin/executable-lines

| Metric | Description |
|---|---|
| Lines to Cover | The number of lines of code that could be covered by unit tests. For example, blank lines or full comment lines are not considered lines to cover. |
| Uncovered Lines | The number of conditions that are not covered by unit tests. |
| Line Coverage | On a given line of code, line coverage answers the question: “Has this line of code been executed during the execution of the unit tests?” It is the density of covered lines by unit tests.<br><br>**Formula:**<br>`Line coverage = LC / EL`<br><br>Where:<br>`LC = covered lines = lines_to_cover - uncovered_lines`<br>`EL = total number of executable lines = lines_to_cover` |

## Duplications

| Metric | Description |
|---|---|
| Duplicated Blocks | The number of duplicated blocks of lines.<br><br>For a block of code to be considered duplicated:<br><br>**Non-Java projects:**<br>- There should be at least 100 successive and duplicated tokens.<br>- Those tokens should be spread across at least:<br>  - 30 lines of code for COBOL<br>  - 20 lines of code for ABAP<br>  - 10 lines of code for other languages<br><br>**Java projects:**<br>There should be at least 10 successive and duplicated statements, regardless of the number of tokens and lines. Differences in indentation and string literals are ignored while detecting duplications. |
| Duplicated Files | The number of files involved in duplications. |
| Duplicated Lines | The number of lines involved in duplications. |
| Density/Duplicated Lines (%) | Percentage of duplicated lines in the codebase.<br><br>**Formula:**<br>`duplicated_lines / lines_of_code * 100` |

## Size

| Metric | Description |
|---|---|
| Lines of Code | The number of physical lines that contain at least one character which is neither whitespace, tabulation, nor part of a comment. |
| Lines | The number of physical lines, based on the number of carriage returns. |
| Statements | The number of statements. For example, `x = 5; y = 10; print(x + y)` contains 3 statements. |
| Functions | The number of functions. Depending on the language, a function is defined as either a function, a method, or a paragraph.<br><br>Language-specific details:<br>- COBOL: It is the number of paragraphs.<br>- Java: Methods in anonymous classes are ignored.<br>- VB.NET: Accessors are not considered to be methods. |
| Classes | The number of classes, including nested classes, interfaces, enums, and annotations. |
| Files | The number of files. |
| Comment Lines | The number of lines containing either comments or commented-out code.<br><br>Non-significant comment lines, such as empty comment lines or comment lines containing only special characters, do not increase the number of comment lines.<br><br>Language-specific details:<br>- COBOL: Generated lines of code and pre-processing instructions such as `SKIP1`, `SKIP2`, `SKIP3`, `COPY`, `EJECT`, and `REPLACE` are not counted as lines of code.<br>- Java: File headers are not counted as comment lines because they usually define the license. |
| Comments (%) | The comment lines density.<br><br>**Formula:**<br>`comment lines / (lines of code + comment lines) * 100`<br><br>With this formula:<br>- 50% means that the number of lines of code equals the number of comment lines.<br>- 100% means that the file only contains comment lines. |

Example of comment line counting:

```java
/**                         // +0 empty comment line
 *                          // +0 empty comment line
 * This is my documentation // +1 significant comment
 * although I don't         // +1 significant comment
 * have much                // +1 significant comment
 * to say                   // +1 significant comment
 *                          // +0 empty comment line
 *************************** // +0 non-significant comment
 *                          // +0 empty comment line
 * blabla...                // +1 significant comment
 */                         // +0 empty comment line

/**                         // +0 empty comment line
 * public String foo() {    // +1 commented-out code
 *   System.out.println(message); // +1 commented-out code
 *   return message;        // +1 commented-out code
 * }                        // +1 commented-out code
 */                         // +0 empty comment line
```

## Complexity

Complexity refers to the number of linearly independent paths in code. It measures how simple or complicated the control flow of the application is.

| Metric | Description |
|---|---|
| Cyclomatic Complexity / Complexity | Cyclomatic complexity is a quantitative metric used to calculate the number of paths through the code.<br><br>Whenever the control flow of a function splits, the complexity counter is incremented by one. Each function has a minimum complexity of 1. This calculation varies slightly by language because keywords and functionalities differ.<br><br>Examples of constructs that may increase complexity include `if`, `for`, `while`, `case`, `catch`, `&&`, `\|\|`, and similar control-flow structures depending on the programming language. |
| Cognitive Complexity | Cognitive Complexity measures how hard it is to understand the code’s control flow.<br><br>**Three Rules of Calculation:**<br><br>1. **Ignore shorthand:** SonarQube does not calculate shorthand structures that make the code easier to read.<br><br>2. **Increment for breaks in linear flow:** SonarQube increases the score when the code flow no longer follows a straight line from top to bottom.<br><br>3. **Increment for nesting:** SonarQube adds extra score when a branch is located inside another branch. |

### Cognitive Complexity Examples

#### 1. Ignore shorthand

Longer version:

```java
if (a != null) {
    myObj = a.myObj;
}
```

Shorthand version:

```java
myObj = a?.myObj;
```

The shorthand version is easier to read, so SonarQube does not penalize it in the same way.

#### 2. Increment for breaks in linear flow

```python
def check_score(score):
    if score >= 50:  # +1 because the flow branches
        return "Pass"
    return "Fail"
```

#### 3. Increment for nesting

```python
def check_score(score, attendance):
    if score >= 50:        # +1
        if attendance >= 80:  # +1 for if, +1 for nesting
            return "Pass"
        return "Review"
    return "Fail"
```
